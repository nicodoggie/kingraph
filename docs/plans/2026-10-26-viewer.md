# Kingraph Viewer Design and Implementation Plan

> **For Hermes:** The user approved this architecture and implementation. Apply subagent-driven-development and tdd-review-workflow. Work is on feat/viewer, based on the committed adapter milestone; pushing, publication and BF migration remain out of scope.

**Goal:** Package BF's useful family-diagram viewing experience as a framework-neutral Kingraph viewer with a native Astro component, without replacing Graphviz or requiring React.

**Architecture:** Use @panzoom/panzoom for gesture handling and transforms, with a light-DOM custom element owning viewer controls and lifecycle. A thin Astro component emits static inline SVG and initializes that same element through a bundled client script. The viewer consumes rendered SVG; renderer and document semantics stay separate.

**Tech Stack:** Existing TypeScript/ESM, Vite, Vitest/Chromium, native custom elements/dialog/fullscreen/ResizeObserver, plus @panzoom/panzoom and Astro development tooling.

## Accepted direction and scope

- Engine: @panzoom/panzoom, not @sasza/react-panzoom or its separate panzoom-core engine. Panzoom documents direct SVG support, pointer/pinch gestures and exclusions for interactive content.[11]
- Retain Graphviz for layout and SVG generation. Smooth viewport motion can be considered now; animated layout transitions, renderer replacement and a general renderer-adapter framework are deferred.
- Preserve the useful BF interaction baseline: inline pan/zoom, optional modal expansion and optional fullscreen. Add explicit zoom/fit/reset controls and preserve native SVG links/tooltips.
- Deliver a reusable browser component and a native Astro wrapper in Kingraph. BF remains a read-only reference and eventual consumer; migrating BF is a separately authorized cross-repository task.
- Keep references, cross-tree resolution, Back history and automatic tree navigation outside this iteration. A small view-state interface may support manual preservation without promising that later system now.
- The committed adapter milestone is 8f2fe90 on feat/date-age-adapters. Viewer implementation is isolated on feat/viewer. Baseline verification passed all 150 Node/core tests before adding the selected engine and Astro development dependencies.

## Recommended public surfaces

### General browser component

Use a separate `@nicodoggie/kingraph/viewer` entry exporting `defineKingraphViewer(): Promise<CustomElementConstructor>`, `KingraphViewerElement` and `ViewerView`. Calling registration explicitly defines `<kingraph-viewer>` once and returns its constructor; module import alone must not access DOM globals or register anything. In particular, do not evaluate `extends HTMLElement` at server import time. The root renderer, `/browser`, CLI and schema entries must not re-export this DOM layer.

Load Panzoom lazily inside asynchronous registration, then define the class with synchronous per-instance lifecycle callbacks. Parent native Node inspection found that @panzoom/panzoom 4.6.2's package main imports with no ESM exports, while browser bundlers use its declared ESM module. Do not introduce a static default import that breaks native server imports of the viewer, or duplicate the engine implementation. Registration is client-side; a server registration call must reject clearly. Repeated/concurrent registration must resolve to the same registered constructor.

Use light DOM, not a closed shadow tree, so SVG links, host styling and progressive enhancement remain straightforward. The element contains one authored/rendered inline SVG. It must not import YAML parsing, Graphviz or rasterization just to display that SVG. Input is trusted SVG under Kingraph's existing authoring boundary, not an untrusted-HTML sanitizer.

Expose a small element interface: `fit()`, `reset()`, `zoomIn()`, `zoomOut()`, `getView(): ViewerView` and `setView(view: ViewerView)`, with typed `{ x, y, scale }` state. Define x/y as pre-scale pan offsets in local content pixels, and scale as CSS viewport pixels per local content pixel; the engine source applies `scale(scale) translate(x, y)`. Normalize the SVG's rendered intrinsic dimensions to its viewBox width/height, retaining its original viewBox and Graphviz's internal transforms. Initial reset returns to the fitted baseline for the current viewport, not an arbitrary scale of one. View-state preservation is scoped to the same SVG/geometry; it does not imply that identical offsets make sense in another tree. Validate finite offsets and positive finite scale at the public setView boundary; use practical documented scale limits rather than a separate generic schema.

The real engine proof verified that Panzoom treats the outer SVG as an HTML-like transform target: retain its default center origin `(w/2,h/2)`, not a forced top-left origin. With fixed intrinsic width w/height h, the content point q maps to `origin + scale * (q + pan - origin)`. Fit pan is `((W-w)/(2*scale), (H-h)/(2*scale))` for viewport W/H. Native background drag and excluded anchor clicks, modifier wheel and emulated Chromium touch/pinch all passed. Linked node boxes are explicitly not pan-start surfaces in this iteration; no custom gesture state machine is necessary. Proof evidence is under `/home/ensu/.hermes/cache/scratch/kingraph-viewer-engine-w9oixkxh/`; useful cases move into the actual viewer tests rather than preserving a redundant dependency test suite permanently.

Prefer one live SVG surface for inline/modal presentation rather than two independent viewer instances with duplicated SVG IDs/state. Modal/fullscreen capabilities are optional, but consumers should not need to reimplement their ordinary controls. Default controls and styling must be replaceable/customizable without exposing the entire underlying Panzoom API as Kingraph's permanent public contract.

### Native Astro component

Use `@nicodoggie/kingraph/astro` as a direct `.astro` component export, default name `KingraphViewer`. Astro's package guidance supports explicit `.astro` subpath exports and requires those source files in the published `files` list.[19]

Props: required rendered `svg: string` and accessible `label: string`; optional `height: string` (default `300px`), `modal: boolean` and `fullscreen: boolean` (both default false), plus native class/style customization. Do not accept both family data and SVG in an ambiguous prop union. Pass the label as aria-label on the custom element. Modal/fullscreen are boolean attributes on the general custom element, absent by default; the Astro wrapper emits the same attributes according to props. Dimensions come from the SVG viewBox rather than requiring callers to duplicate Vite's width/height exports. Use `--kingraph-viewer-height` as the shared height CSS custom property.

The wrapper renders the inline SVG on the server/build side, with a useful static no-JavaScript fallback, and uses a processed `<script>` to import/register the shared browser component. It should require neither a React integration nor a `client:*` hydration directive. Astro documents framework-free custom elements and deduplicated bundled scripts for this purpose.[17]

The existing `family.yaml?kingraph&raw` import is the natural input. Adapters and asOf remain render/Vite configuration; their functions and the Graphviz engine do not become browser viewer dependencies. The Astro wrapper should be usable in a normal Astro page and through an Astro/MDX consumer.

## Interaction and lifecycle requirements

- Let Panzoom own gesture mathematics. Use its supported configuration/hooks before introducing custom gesture machinery.[11]
- Resolve link click versus drag explicitly with an actual Graphviz-linked node. Panzoom's documented exclusion approach makes links clickable but also excludes them from pan initiation.[11] Start by exercising this supported behavior. If dragging from linked node boxes is required and exclusions are inadequate, identify the smallest hook-based solution and review it before creating a second pointer/gesture state machine.
- Wheel interaction must not trap ordinary document scrolling accidentally; choose an explicit desktop modifier/activation policy and test it. Touch gestures must remain usable on the viewer without claiming that one-finger page scrolling and one-finger diagram panning can both own the same gesture.
- Default wheel policy is Ctrl/Meta + wheel to zoom in every presentation; ordinary wheel is not cancelled. Show a concise hint. Let Panzoom own touch/pinch interaction within the viewport, with normal page scrolling remaining available outside it. Default methods apply transforms without animation; reduced-motion users therefore never receive mandatory viewport animation.
- Provide accessible button names, keyboard-operable controls, a meaningful non-modal inline region, modal focus restoration and native Escape behavior. Respect reduced-motion preferences for optional viewport animations. Fullscreen is a capability that can be unavailable/denied; preserve modal/inline operation rather than report that fullscreen succeeded.
- Fit after the surface has measurable dimensions. Observe container resizing; do not cache the initial hidden-dialog size permanently. Decide whether modal expansion preserves the viewed content center or intentionally refits, and make that behavior explicit rather than accidentally resetting state.
- On first measurable connection fit and center; later resize or modal expansion preserves the viewed content center and absolute scale. Reset/Fit intentionally recompute the current fitted view. Keep one live viewport/SVG surface when entering/leaving a native dialog, retaining one Panzoom instance, with an inline placeholder for restoring its position. Default controls are keyboard-operable buttons; a caller-supplied `data-kingraph-controls` toolbar can replace them using `data-kingraph-action` button values documented by the implementation. Avoid a second template/control system.
- Initialize each element instance on connection and release its Panzoom handlers, wheel listeners, observers and owned modal/fullscreen state on disconnect. Reconnection must be safe without duplicated listeners or controls. Only exit fullscreen owned by that viewer, never another component's session.
- Astro's bundled scripts execute only once across client-side page transitions, so a one-time global querySelector initialization is insufficient.[18] Custom-element connection/disconnection is the preferred instance lifecycle. Qualify real ClientRouter navigation and multiple viewers; avoid an additional global Astro event dispatcher unless native lifecycle proof exposes a specific gap.
- Do not claim support for persisting a viewer while replacing its SVG content merely because ordinary navigation works. Dynamic content replacement and cross-tree navigation need their own later contract.

## Packaging and likely files

- Create browser implementation and types in `src/viewer.ts`; use small supporting files only when they isolate a real lifecycle/markup responsibility.
- Create `astro/KingraphViewer.astro`, shipped as source. TypeScript's current build does not compile Astro files; do not pretend it does or re-export `.astro` from the Node renderer barrel.
- Add a shipped stylesheet with an explicit viewer-only export, deciding source-versus-emitted location consistently with the native build. Reuse one stylesheet between plain-browser and Astro consumers. Do not make existing core consumers import viewer CSS.
- Update `package.json` and `package-lock.json` for viewer exports, the actual shipped Astro/CSS files, Panzoom, and scoped Astro development/optional-peer metadata. Keep Astro optional for non-Astro consumers; no React dependency. Start qualification on BF's Astro 7 line, grounding the peer range in actual exercised versions rather than claiming all Astro versions.
- Add focused tests in `tests/browser/viewer.browser.ts` and a real Astro-consumer integration test in `tests/astro.test.ts` or an equally narrow existing-runner fixture. Update tsconfig/format/typecheck discovery only for the file kinds actually introduced; use native Astro tooling for `.astro` types/compilation.
- Update README and a viewer-specific guide. Keep package source/fixtures/evidence out of BF unless that migration receives explicit approval.

## Implementation and verification sequence after design approval

1. **Bounded engine/linked-SVG proof.** Exercise the selected Panzoom version with a real Kingraph SVG, linked nodes and native controls. Prove the chosen click/drag, wheel/touch and fit behavior before freezing the public element interface. Prefer configuration and mature hooks over a custom gesture implementation. This is not a new multi-library selection campaign; the engine choice is settled.
2. **General viewer vertical slice.** Implement registration, inline progressive enhancement, controls and view-state operations with focused behavioral RED/GREEN at actual lifecycle/interaction seams. Add optional modal/fullscreen to the same surface with cleanup, resize and failure behavior. Keep import/SSR safety covered by native import/type/build evidence instead of source-string tests.
3. **Astro package integration.** Add the source wrapper, exports and styles in the same usable slice. Build a disposable Astro consumer using the packaged component, native raw YAML import and actual browser interactions. Test more than one instance and ClientRouter navigation/teardown. The wrapper's compilation, type support and CSS/script output must be verified with native Astro tooling, not assumed from plain Vite success.
4. **Installed-consumer acceptance and review.** Run the existing `npm test`, `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run test:browser` and `git diff --check` after adapting their native scopes as needed. Pack/install into disposable plain-browser and Astro consumers and prove their public imports, progressive enhancement and real interaction. Inspect emitted client dependencies to confirm no Graphviz, YAML parser, resvg, React or Astro runtime leaked into the general viewer bundle. Use one representative behavioral matrix, not duplicated tests for every Panzoom helper. Review the bounded public contract and implementation; no push/publication or BF migration is implicit.

## Execution boundary

The general light-DOM custom element and thin native Astro wrapper are separate optional entry points. The defaults above resolve the draft's open behavior choices. The engine proof must verify the transform and link-exclusion assumptions before building on them; report a concrete mismatch rather than inventing a competing gesture engine. Parent owns manifests/exports/dependency selection and final acceptance. Leaf workers must keep disjoint changed-path sets, use explicit scratch roots for temporary fixtures and avoid commits or publication.
